# UI Kit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Construir `/ui-kit`, una página pública y única que cataloga visualmente todos los componentes reales de la aplicación, sus variantes y sus estados, legible de un tirón por un humano o por un LLM.

**Architecture:** Una ruta fuera del árbol autenticado, con shell propio (cabecera con conmutador de tema + índice lateral de anclas + `main`). El contenido se declara con cinco primitivas de andamiaje que garantizan HTML semántico e idéntico en las más de sesenta fichas. Los overlays basados en portal se catalogan por duplicado: trigger real más réplica inline siempre presente en el DOM.

**Tech Stack:** Vite, React 19, TypeScript, Tailwind CSS v4, shadcn/ui sobre `radix-ui`, react-router, lucide-react, sonner. No se añade ninguna dependencia.

**Spec:** [docs/superpowers/specs/2026-08-30-ui-kit-design.md](../specs/2026-08-30-ui-kit-design.md)

## Global Constraints

- Node.js >= 20. Nunca añadir dependencias: el `package.json` no se toca.
- **Prohibido modificar cualquier archivo de `src/components/ui/`.** Es el criterio de aceptación final de la spec.
- Los únicos archivos existentes que se modifican son `src/app.tsx` (una ruta) y `src/index.css` (una línea, en la Task 4). Ningún otro.
- Idioma: los títulos de sección y las descripciones de una línea van en español. Las etiquetas de variante, tamaño y estado usan el valor literal del prop, en inglés: `default`, `outline`, `destructive`, `icon-sm`, `disabled`, `aria-invalid`.
- Datos mock: solo desde `src/data/users.ts` y `src/data/api-keys.ts`. Nunca datos de personas reales.
- La página no muestra código, ni props, ni snippets, ni botones de copiar.
- Nada de tabs, accordions cerrados, modales-como-vitrina ni rutas hijas de `/ui-kit`.
- Ninguna acción del catálogo persiste nada ni navega fuera de la página.
- Todos los archivos nuevos viven bajo `src/pages/ui-kit/`.
- Import alias: `@/` apunta a `src/`. Usarlo siempre, como el resto del proyecto.
- Comillas dobles, sin punto y coma final: lo impone Prettier vía `npm run format`.

### Ciclo de verificación

**Este proyecto no tiene framework de tests y añadir uno queda fuera del alcance de la spec.** El diseño original del starter fija «Tests: ninguno». En lugar de TDD, cada tarea se cierra con esta verificación, y ninguna se da por hecha sin ejecutarla:

```bash
npm run typecheck && npm run lint
```

Más una comprobación en el navegador contra el dev server. Para levantarlo se usa el preview del proyecto (`.claude/launch.json`, entrada `shadcn-starter`), **nunca** `npm run dev` desde una shell. Cada tarea trae las aserciones exactas a ejecutar en la consola del navegador; todas devuelven un número o un booleano comprobable, no una impresión visual.

```tsx
import type { ReactNode } from "react"
import { cn } from "@/lib/utils"

export function KitSection({
  id,
  title,
  description,
  children,
}: {
  id: string
  title: string
  description: string
  children: ReactNode
}) {
  return (
    <section id={id} className="scroll-mt-28">
      <div className="border-b pb-3">
        <h2 className="text-2xl font-semibold tracking-tight">{title}</h2>
        <p className="mt-1 text-sm text-muted-foreground">{description}</p>
      </div>
      <div className="mt-8 flex flex-col gap-10">{children}</div>
    </section>
  )
}

export function KitComponent({
  id,
  name,
  description,
  children,
}: {
  id: string
  name: string
  description: string
  children: ReactNode
}) {
  return (
    <article id={id} className="scroll-mt-28">
      <h3 className="text-base font-medium">{name}</h3>
      <p className="mt-0.5 text-sm text-muted-foreground">{description}</p>
      <div className="mt-4 flex flex-col gap-6 border p-4">{children}</div>
    </article>
  )
}

export function KitGroup({
  label,
  children,
}: {
  label: string
  children: ReactNode
}) {
  return (
    <div>
      <h4 className="mb-3 text-xs font-medium text-muted-foreground">{label}</h4>
      {children}
    </div>
  )
}

export function KitRow({
  children,
  className,
}: {
  children: ReactNode
  className?: string
}) {
  return (
    <div className={cn("flex flex-wrap items-start gap-x-6 gap-y-4", className)}>
      {children}
    </div>
  )
}

export function KitSpecimen({
  label,
  children,
  className,
}: {
  label: string
  children: ReactNode
  className?: string
}) {
  return (
    <div className={cn("flex min-w-0 flex-col gap-2", className)}>
      <span className="font-mono text-xs text-muted-foreground">{label}</span>
      {children}
    </div>
  )
}
```

```tsx
import { useEffect } from "react"
import { useTheme, type Theme } from "@/components/theme-provider"
import { ToggleGroup, ToggleGroupItem } from "@/components/ui/toggle-group"
import { TooltipProvider } from "@/components/ui/tooltip"
import { UI_KIT_SECTIONS } from "@/pages/ui-kit/ui-kit-nav"

const THEME_OPTIONS: { value: Theme; label: string }[] = [
  { value: "light", label: "Claro" },
  { value: "dark", label: "Oscuro" },
  { value: "system", label: "Sistema" },
]

// Invariante de la spec: todo id declarado en `ui-kit-nav.ts` debe existir en el
// DOM. Se comprueba solo en desarrollo, para que un ancla rota se detecte al
// añadir una ficha en lugar de descubrirse al hacer clic meses después.
function useDeclaredIdCheck() {
  useEffect(() => {
    if (!import.meta.env.DEV) return

    const declared = UI_KIT_SECTIONS.flatMap((section) => [
      section.id,
      ...section.entries.map((entry) => entry.id),
    ])
    const missing = declared.filter((id) => document.getElementById(id) === null)

    if (missing.length > 0) {
      console.error(
        `[ui-kit] ids declarados en ui-kit-nav.ts sin elemento en el DOM: ${missing.join(", ")}`,
      )
    }
  }, [])
}

export function UiKitPage() {
  const { theme, setTheme } = useTheme()
  useDeclaredIdCheck()

  return (
    <TooltipProvider>
      <div className="min-h-svh bg-background text-foreground">
        <header className="sticky top-0 z-40 flex flex-col gap-3 border-b bg-background px-6 py-3 sm:flex-row sm:items-center sm:justify-between">
          <div>
            <h1 className="text-lg font-semibold">UI Kit</h1>
            <p className="text-sm text-muted-foreground">
              Referencia visual del sistema. Todos los datos son ficticios.
            </p>
          </div>
          <ToggleGroup
            type="single"
            variant="outline"
            spacing={0}
            value={theme}
            onValueChange={(value) => {
              if (value) setTheme(value as Theme)
            }}
            aria-label="Tema"
          >
            {THEME_OPTIONS.map((option) => (
              <ToggleGroupItem key={option.value} value={option.value}>
                {option.label}
              </ToggleGroupItem>
            ))}
          </ToggleGroup>
        </header>

        <div className="mx-auto flex w-full max-w-7xl gap-10 px-6">
          <aside className="sticky top-28 hidden h-fit w-44 shrink-0 py-10 lg:block">
            <nav aria-label="Secciones del UI Kit">
              <ul className="flex flex-col gap-0.5">
                {UI_KIT_SECTIONS.map((section) => (
                  <li key={section.id}>
                    <a
                      href={`#${section.id}`}
                      className="block px-2 py-1 text-sm text-muted-foreground hover:bg-muted hover:text-foreground"
                    >
                      {section.title}
                    </a>
                  </li>
                ))}
              </ul>
            </nav>
          </aside>

          <main className="flex min-w-0 flex-1 flex-col gap-16 py-10"></main>
        </div>
      </div>
    </TooltipProvider>
  )
}
```

- [ ] **Step 1: Habilitar la isla de tema claro**

La ficha Colors muestra las dos paletas a la vez. Una isla `.dark` funciona sola, pero una isla clara dentro de `html.dark` no tiene forma de recuperar los valores de `:root`.

Modificar `src/index.css`, línea 53. Cambiar exactamente esto:

```css
:root {
```

por esto:

```css
:root, .light {
```

Es un cambio de una línea y **cero duplicación de tokens**: los valores claros siguen declarados una sola vez, y ahora `<div class="light">` los restaura para sus descendientes esté donde esté. No altera el comportamiento actual, porque `:root` sigue aplicando a `<html>`.

Limitación conocida, que solo afecta a esta ficha: dentro de la isla clara, las utilidades `dark:` de Tailwind siguen activas si la página está en oscuro, porque el variant está definido como `&:is(.dark *)`. Los swatches de color no usan ninguna utilidad `dark:`, así que no les afecta. Por eso la isla se usa **solo** para muestras de token, nunca para especímenes de componente.

### Task 8: Réplicas inline de los overlays

**Interfaces:**
- Consumes: `Dialog`, `DialogHeader`, `DialogTitle`, `DialogDescription`, `DialogFooter`; `AlertDialog` y familia; `Sheet` y familia; `cn`.

**Por qué existe este archivo.** La spec preveía un helper por overlay dentro de cada archivo de sección. En la práctica, la réplica del menú la necesitan tres secciones distintas — Navigation, Overlays y Composite — así que se centraliza en un único módulo. Se mantiene el objetivo de la spec: un solo sitio donde vive la duplicación, localizable con un `grep`.

**Dos regímenes distintos, y hay que respetarlos:**

- `DialogTitle`, `DialogDescription`, `SheetTitle`, `SheetDescription`, `AlertDialogTitle` y `AlertDialogDescription` son primitivos de Radix que solo necesitan el contexto del **Root**. Envolviéndolos en `<Dialog open>` funcionan fuera del `Content`, sin portal y sin bloqueo de scroll. Estas réplicas **reutilizan los subcomponentes reales** y solo duplican la superficie exterior.
- `DropdownMenuItem` y `SelectItem` exigen el contexto del **Content** y **lanzan** si se renderizan fuera de él. Sus réplicas tienen que duplicar también el marcado del ítem. Es más duplicación de la que preveía la spec, y es inevitable sin tocar los primitivos.

## Notas de desviación respecto a la spec

Tres puntos donde la implementación se aparta del documento de diseño, descubiertos al planificar. Ninguno cambia el objetivo; los tres lo cumplen mejor.

1. **`src/index.css` se modifica en una línea** (`:root` pasa a `:root, .light`). La spec no lo previó. Sin ello, la ficha Colors no puede mostrar la paleta clara cuando la página está en tema oscuro. La alternativa era duplicar los 31 tokens; esta no duplica ninguno.

2. **Las réplicas viven en `src/pages/ui-kit/replicas.tsx`**, no repartidas por archivo de sección como decía la spec §3.6. La réplica de menú la necesitan tres secciones distintas. El objetivo de la spec —un solo sitio localizable donde vive la duplicación— se cumple igual o mejor.

3. **`DropdownMenuItem` y `SelectItem` no se pueden reutilizar en las réplicas**, al contrario de lo que daba por hecho la spec §3.6: son primitivos de Radix que lanzan fuera de su `Content`. Su marcado se replica en `replicas.tsx`. `DialogTitle` y familia sí se reutilizan, porque les basta el contexto del `Root`.

Un cuarto punto, que la spec dejaba implícito y este plan hace explícito: **los compuestos que dependen de la sesión o de la ruta se recomponen con datos mock** (`AppSidebar`, `SiteHeader`, `NavUser`, `LoginPage`), porque en una página pública devolverían `null`, mostrarían la ruta equivocada o ejecutarían acciones reales. Los compuestos puros (`DataTable`, `CreateKeyDialog`) se montan tal cual.
